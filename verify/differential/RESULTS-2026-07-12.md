# Differential results & throughput baseline — 2026-07-12

First run of the differential-testing harness (V6/V7) and the throughput
baseline (brief §8.2). This report follows brief §5: **disagreements are
findings, listed in full, never reclassified.**

## TL;DR

- **The harness found 20 real disagreements.** On Lean core `Init.Prelude`,
  oxilean-verify **rejects** 20 `*.noConfusion` declarations that both lean4lean
  and the Lean C++ kernel **accept**. All 20 trace to **3 root rejections** —
  `noConfusion` for multi-constructor inductives (`Lean.ParserDescr`,
  `Lean.Name`, `Lean.SourceInfo`). This is an **oxilean-kernel completeness bug**
  (a false rejection), surfaced exactly as differential testing is meant to.
- **Where both checkers reach a verdict, they otherwise agree** (1556 AGREE,
  0 agree-but-opposite outside the 20 above).
- **Throughput baseline (lean4lean):** ~**3,280 decls/sec** end-to-end on
  `Init.Prelude` (1935 decls, median 0.59 s, ~100 MB RSS).
- **Our throughput:** ~**376 decls/sec** on the same `Init.Prelude` set (1814
  decls, median 4.83 s). That is **~8.7× below** the lean4lean baseline — outside
  the brief's "within 5×" budget. An honest number, recorded as a target.

### Version skew (a caveat, not a blocker — brief §8.2)

lean4lean `master` pins **v4.29.0**; our reader/corpus are **v4.32.0-rc1**. No
lean4lean branch/tag targets v4.32.0-rc1 (newest: `arena-v4.27.0-rc1`,
`v4.27.0-rc1`), so `master` (v4.29.0) is the nearest workable choice. Consequence:
the two checkers' declaration *sets* differ, so a chunk of decls appear on only
one side (**ONLY-ONE-SIDE**), which is skew, not conflict. The 20 disagreements
below are **not** skew: their declarations are present, checked, and verdicted on
both sides.

Also noted (README "lean4lean status"): lean4lean's default `replayFromImports`
path **segfaults** on this toolchain in region-teardown (`lean_dec_ref_cold` from
`lean4lean_replayFromImports`, worker thread). We drive it with **`--fresh`**
(the `replayFromFresh` path), which runs cleanly to `checked N declarations`.

Every one is `oxilean=rejected` vs `lean4lean=verified`. Lean's own C++ kernel

### Root cause (characterization)

The three root rejections are all `TypeMismatch` errors when the kernel checks a
`.noConfusion` definition against its declared type. The definition's body is the
standard `noConfusion` shape (`fun t => noConfusionType … t …` applied through the
recursor), and oxilean-kernel's inferred type of that body diverges from the
declared type for inductives with **more than the trivial constructor count**.
The mismatch is in how `noConfusionType`'s per-constructor branches reduce (the
`expected` vs `got` Pi-telescopes differ in their tail; see the full `detail`
strings in `artifacts/oxilean.Init.Prelude.jsonl`). The dependents are pure
cascade — oxilean-verify correctly refuses to build on a rejected dependency and
labels them `depends on rejected declaration '…'`.

The same pattern reappears on the wider corpus: the 2,000-decl Init slice adds a
fourth root, `Std.IterStep.noConfusion` (a newer, v4.32.0-only type — hence
ONLY-ONE-SIDE against lean4lean's v4.29.0), with 3 dependents. So this is a
**single systematic bug** in `noConfusion` handling, not four unrelated ones.

**Action:** this belongs in the kernel `noConfusion`/`noConfusionType` code path
(`oxilean-kernel`). It is a completeness bug (a false `rejected`), tracked as a
verify-campaign finding. It does not implicate export/reader/verify plumbing:
the reader parsed these decls fine and the verdict flowed correctly.

## Throughput baseline (brief §8.2)

Measured on the **same** `Init.Prelude` declaration set so the numbers are
comparable. lean4lean timing is end-to-end (`lake env … lean4lean --fresh`,
including import loading and process startup); oxilean-verify timing is
end-to-end (`oxilean-verify … file.ndjson`).

| checker | set | decls | median wall | decls/sec | RSS |
|---|---|---|---|---|---|
| **lean4lean** (baseline) | Init.Prelude (v4.29.0 oleans) | 1935 | 0.59 s | **~3,280** | ~100 MB |
| **oxilean-verify** | Init.Prelude (v4.32.0 NDJSON) | 1814 | 4.83 s | **~376** | (< 0.5 GB) |

**oxilean-verify is ~8.7× slower** per declaration than the lean4lean baseline on
this set — outside the "within 5×" budget. This is the honest starting number the
brief asked us to measure rather than guess; closing it is future work (the
kernel's reduction/def-eq hot path is the obvious target).

## Additional finding: oxilean-verify stack overflow on full `Init.ndjson`

Checking the **whole** 57,277-decl `Init.ndjson` in one process **overflows the
main-thread stack** (`thread 'main' has overflowed its stack, fatal runtime
error`) after ~90 s at ~3.5 GB RSS — with and without `--json-full`, and with
`RUST_MIN_STACK=512M` (which only affects spawned threads, not `main`). A run
with a large `ulimit -s` is required to complete the full corpus. This is a
recursion-depth issue in the checker/reader on deeply-nested declarations, worth
a follow-up (either bound the recursion or drive checking on a large-stack
worker thread). It does not affect the Init.Prelude comparison above, which
completes comfortably.

## Post-fix re-run — 2026-07-15 (oxilean-verify 0.1.3)

The 20 disagreements above were diagnosed as a single systematic
oxilean-kernel completeness bug in `noConfusion` checking. Two kernel fixes
landed on the 0.1.3 tree since this report was first written:

- `2dd4c78` — def-eq opens binders with **typed locals**, so K-like iota sees
  the local context (C15; the `noConfusion` root cause), and
- `024399e` — structure-eta of stuck recursor majors (Lean `toCtorWhenStruct`).

The oxilean leg was re-run on the **same declaration set** (`Init.Prelude`
re-exported with the pinned v4.32.0-rc1 lean4export, 1814 decls) and re-joined
against the **unchanged, recorded** lean4lean verdicts
(`artifacts/lean4lean.Init.Prelude.jsonl`):

```
total distinct declarations joined: 1987

comparison buckets:
  AGREE (both verified or both rejected) : 1576   (was 1556)
  DISAGREE (verified vs rejected)        : 0      (was 20)  <-- all findings closed
  ONLY-ONE-SIDE (version/toolchain skew) : 228    (unchanged)
  UNSUPPORTED-SKIPPED (one side declines): 183    (unchanged)

oxilean   per-verdict: verified 1631 · rejected 0 · unsupported 183 · absent 173
lean4lean per-verdict: verified 1932 · rejected 0 · unsupported   0 · absent  55
```

**20 → 0 disagreements.** All 20 previously false-rejected `*.noConfusion`
declarations (3 roots + 17 cascade dependents) are now `verified`, and every
one of the +20 landed in AGREE — no declaration changed verdict in any other
direction. `diff_verdicts.py --fail-on-disagree` exits 0. Post-fix evidence is
committed beside the originals: `artifacts/oxilean.Init.Prelude.postfix.jsonl`,
`artifacts/join.Init.Prelude.postfix.{csv,md}`.

fully checked instead of erroring out early) and throughput still improved
slightly. Root cause remains the kernel's tree-shaped `Expr` (no structural
sharing/hash-consing), which is the deliberate, tracked follow-up — see
`TODO_VERIFY.md`.

### Stack-overflow follow-up: FIXED

The "additional finding" above (main-thread stack overflow on the full 57,277-decl
`Init.ndjson`) was fixed on the 0.1.3 tree (C16/C17: iterative whnf + a dedicated
verify thread with configurable stack). The full-corpus run now completes with
exit 0: **35,223 verified · 22,054 unsupported · 0 rejected** — see
`docs/reports/2026-07-15-lean-core-init.md`.
